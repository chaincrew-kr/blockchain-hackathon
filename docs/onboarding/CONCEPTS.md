## 0. 한 줄 요약 — 지금 우리가 만든 것

> **AI 에이전트가 사람 개입 없이 API 사용료를 스스로 결제할 수 있게 하는 "결제
> 인프라"를, Solana devnet에서 실제로 동작시켰다.**

⚠️ **중요 (헷갈리기 쉬운 부분):** 지금 코드에는 **아직 "AI"가 들어있지 않습니다.**
우리가 만든 건 AI의 **손발(결제 기능)**이고, 그 손발을 조종할 **뇌(AI 판단
로직)**는 다음 단계에서 얹습니다. 자세한 건 [7번](#7-그래서-뭐가-ai인가--ai-에이전트-빌드업)
참고. 지금 단계 이름을 붙이자면 **"AI 에이전트 빌드업(build-up)"** 입니다.

⚠️ **해커톤 관점의 위치 (더 중요):** 수상작 분석([notice](../notice/solana_top25_winners_analysis_light.html))에
따르면 심사는 "결제 기술이 돌아간다"가 아니라 **"누가 실제로 돈을 내는가, Solana가
빠지면 성립 안 하는가, 쓸수록 데이터가 쌓이는가"** 같은 **제품 질문**을 봅니다. 즉 이
결제 레일은 제품이 아니라 **제품의 한 레이어(Resource Execution)** 입니다. 그 위에
얹을 제품 주제(예: OpenBench — 흩어진 AI 실험을 검증 가능한 공동 지식으로 바꾸고
재사용 가치에 따라 API 연구자원을 배분하는 실험 인텔리전스 네트워크)는 **팀 논의
중**이며, 이 온보딩은 팀원이 그 제품을 이 레일 위에 얹을 수 있게 하는 기초입니다.

## 1. 이 프로젝트가 대체 뭘 하는 건데?

유료 API가 있고, 그걸 **자동으로 결제하고 쓰는** 클라이언트가 있습니다.

```
1. 클라이언트: "데이터 줘"                 (돈 없이 요청)
2. 서버:      "402 Payment Required, $0.001 내"
3. 클라이언트: 블록체인으로 결제 → 결제 증명을 붙여 다시 요청
4. 서버:      "결제 확인됨. 200 OK, 데이터 여기"
```

핵심은 2~3번이 **사람 손 없이 자동**으로 일어난다는 것. 카드 긁고 버튼 누르는 과정을
코드가 개인키로 대신합니다.

## 2. x402가 뭐야?

**HTTP로 돈을 주고받는 표준 규칙(프로토콜)** 입니다. 이름의 유래:

웹에는 **HTTP 상태 코드**가 있습니다 — 서버 응답에 붙는 숫자표예요.

- `200` = 성공, `404` = 없음, **`402` = Payment Required("돈 내야 함")**

이 `402`는 인터넷 초창기에 "언젠가 결제에 쓰자"고 자리만 만들어두고 **25년 넘게
방치**됐습니다. 마땅한 결제 수단이 없었거든요. **x402는 이 잠자던 402를 깨워
블록체인 결제에 실제로 쓰는 프로토콜**입니다. Coinbase가 주도한 오픈 표준이고,
특히 **AI 에이전트가 자동으로 API 값을 내는** 시나리오에 초점이 있습니다.

## 3. 등장인물 정리 (제일 헷갈리는 부분)

"서버"라고 부를 만한 게 여러 개라 헷갈립니다. 3개로 구분하세요.

| 이름                             | 정체                                                                 | 어디 있나                             | 우리가 만들었나                    |
| -------------------------------- | -------------------------------------------------------------------- | ------------------------------------- | ---------------------------------- |
| **⓪ 구매자 클라이언트 (buyer)**  | `npm run client`로 실행. 402 받으면 서명·재시도로 **결제를 대신** 함 | **각자 본인 PC** (한 번 실행 후 종료) | ✅ 우리가 만듦 (`packages/agent/`) |
| **① API 서버 (resource server)** | `npm run dev`로 켜는 우리 프로그램. "돈 내면 데이터 준다"            | **각자 본인 PC** (`localhost:4021`)   | ✅ 우리가 만듦 (`apps/api/`)       |
| **② facilitator**                | 결제가 진짜인지 검증 + 수수료 대납 + 블록체인 정산 대행              | 외부 (`x402.org/facilitator`)         | ❌ 남이 운영                       |
| **③ 블록체인 (Solana devnet)**   | 실제 장부. 돈 이동이 최종 기록되는 곳                                | 전 세계 분산 네트워크                 | ❌ Solana 것                       |

> **중요 — 우리는 양쪽을 다 만들었습니다.** 원래 x402에서는 판매자가 서버를,
> 구매자(사람·AI)가 클라이언트를 각각 만듭니다. 하지만 해커톤에서는 결제 흐름
> 전체를 혼자 시연해야 하므로, **판매자 서버(①, `apps/api`)와 구매자
> 클라이언트(⓪, `packages/agent`) 양쪽을 모두 우리가 만들었습니다.** 외부에서
> 갖다 쓰는 건 ②facilitator·③Solana 둘뿐입니다.

**"우리 서버는 어디 있냐" = ①번, 본인 PC의 localhost.** `localhost`는 "이 컴퓨터
자신"이라는 뜻이라, 지금은 나만 접속 가능합니다. (외부 공개는 [8번](#8-서버가-로컬인데-키-공유가-의미-있나) 참고)

결제 한 번의 전체 그림:

```
[buyer 클라이언트] ──요청──▶ [① 우리 API 서버]
      │◀── "402, 돈 내" ─────────┘
      │ 결제 서명 후 재시도
      ▼
[① 우리 API 서버] ──"이 결제 진짜야?"──▶ [② facilitator] ──검증/정산──▶ [③ Solana]
      │◀── "유효함" ────────────────────┘
      ▼
[① 우리 API 서버] ──"200 OK + 데이터"──▶ [buyer]
```

즉 **⓪구매자 클라이언트와 ①판매자 서버 양쪽이 우리 코드**이고, ②facilitator·
③Solana만 외부 인프라입니다.

## 4. 지갑 · 주소 · 개인키 · 시드

블록체인 지갑은 **은행 계좌**로 비유하면 쉽습니다.

| 은행               | 블록체인 지갑                  | 공개해도 되나 |
| ------------------ | ------------------------------ | ------------- |
| 계좌번호           | **지갑 주소** (예: `2vNC3...`) | ✅ OK         |
| 비밀번호/도장      | **개인키**                     | ❌ 절대 금지  |
| 비밀번호 복구 문구 | **시드 구문** (12단어)         | ❌ 절대 금지  |

**주소는 어떻게 만들어지나:**

```
무작위 난수  →  개인키  →  공개키(= 지갑 주소)
  (씨앗)      (비밀)        (공개)
```

- 왼쪽 → 오른쪽은 계산이 **쉽고**, 오른쪽 → 왼쪽 역산은 **사실상 불가능**합니다.
- 그래서 **주소는 아무 데나 공개해도 안전**하고(계좌번호처럼), **개인키는 유출되면
  지갑을 통째로 뺏깁니다**.

우리 지갑은 `solana-keygen new` 명령 한 줄로 만들었습니다.

## 5. 왜 지갑을 2개(merchant/buyer)로 나누나

**보안 설계**입니다.

| 지갑                           | 역할                                 | 개인키 필요?       | 어디에 둠                             |
| ------------------------------ | ------------------------------------ | ------------------ | ------------------------------------- |
| **merchant** (판매자, 돈 받음) | 서버가 "여기로 결제해" 알려주는 주소 | ❌ **공개 주소만** | 서버 `.env`의 `SVM_ADDRESS`           |
| **buyer** (구매자, 돈 냄)      | 결제를 서명                          | ✅ 개인키 필요     | 클라이언트 `.env`의 `SVM_PRIVATE_KEY` |

돈을 **받기만** 하는 쪽은 개인키가 필요 없습니다. 그래서 서버엔 공개 주소만 두면,
**서버가 해킹당해도 훔쳐갈 개인키가 없어** 지갑이 안전합니다. 하나로 합치면 서버
쪽에도 개인키가 있어야 해서 위험해집니다.

## 6. devnet이 뭐야? 가짜 블록체인이야?

**"연습용 진짜 블록체인"** 이 정확한 표현입니다. Solana는 장부를 3개 운영합니다.

| 종류        | 용도          | 돈의 가치                 |
| ----------- | ------------- | ------------------------- |
| **Mainnet** | 실전 서비스   | 진짜 돈 (1 USDC ≈ 1달러)  |
| **Devnet**  | 개발자 연습   | **가짜 (0원, 무료 배급)** |
| Testnet     | 검증자 테스트 | 가짜                      |

- **진짜인 부분:** 작동 원리·트랜잭션 처리 방식은 mainnet과 **완전히 동일**. 여기서
  되면 mainnet에서도 됩니다.
- **가짜인 부분:** 여기 도는 SOL·USDC는 **가치가 0**. 그래서 faucet이 공짜로 뿌리고,
  실수로 날려도 손해 0원.

지금 우리 지갑의 SOL·USDC는 전부 0원짜리이니 **마음 편히 테스트**하면 됩니다.
mainnet 전환은 충분히 검증한 뒤에.

## 7. 돈이 2종류인 이유 (SOL vs USDC) + 관련 개념 총정리

결제 한 번에 실제로 돈이 **2군데**로 나갑니다.

| 뭐         | 얼마      | 누구한테          | 무슨 돈  |
| ---------- | --------- | ----------------- | -------- |
| **상품값** | $0.001    | merchant (판매자) | **USDC** |
| **수수료** | 아주 소액 | 네트워크 (검증자) | **SOL**  |

### 에어드랍 / faucet

**faucet(수도꼭지)** = 테스트용 코인을 **공짜로 뿌려주는 사이트**. **에어드랍** =
그 코인을 지갑에 넣어주는 행위. devnet 돈은 가치가 0이라 공짜로 줄 수 있습니다.

- SOL: https://faucet.solana.com/ (GitHub 로그인 시 한도 상승)
- USDC: https://faucet.circle.com/ (**Network를 반드시 `Solana Devnet`으로** 변경 — 기본값 주의)

### ATA("서랍") — USDC는 왜 서랍이 필요한가

Solana에서 **SOL은 지갑에 직접** 담기지만, **USDC 같은 토큰은 전용 하위 계정**에
담깁니다. 이걸 **ATA(Associated Token Account)** = "서랍" 이라고 부릅니다.

```
지갑 (2vNC3...)          ← SOL은 여기 직접
  └── USDC 서랍 (64wTi...) ← USDC는 이 안에
```

- 서랍 주소는 "지갑 + 토큰 종류"로 자동 계산되는 값(랜덤 아님).
- **지갑 만든다고 서랍이 자동 생기지 않습니다.** 그 토큰을 처음 받을 때 누군가
  만들어줘야 하고, 만들 때 SOL 소액(rent)이 듭니다.
- 우리가 겪은 결제 실패(`transaction_simulation_failed`)가 바로 이것 — 받는 쪽
  merchant에 USDC 서랍이 없어서 실패했고, 서랍을 만들어주니 해결됐습니다.
  ([9번](#9-우리가-겪은-삽질-자주-나올-에러) 참고)

### 수수료 대납 — buyer는 사실상 USDC만

원래 buyer는 USDC(상품값) + SOL(수수료) 둘 다 있어야 하지만, x402에서는
**facilitator가 수수료(SOL)를 대신 내줍니다.** 결제 챌린지 안에
`feePayer`(수수료 내는 사람)가 facilitator 주소로 지정돼 있기 때문입니다.

그 결과:

```
buyer가 실제로 내는 것:
  ✅ USDC (상품값)  ← 이것만 나감
  ❌ SOL (수수료)   ← facilitator 대납
```

**왜 이렇게?** 보통 사람·AI는 USDC(달러 같은 돈)는 있어도 SOL(수수료 코인)은 잘
없습니다. "결제하려면 SOL도 따로 챙겨" 하면 진입장벽이 높아지니, 대납으로 **USDC
하나만 신경 쓰면 되게** 만든 것. AI 자동 결제엔 이 단순함이 결정적입니다.

> 단, buyer가 **직접** 다른 트랜잭션(예: merchant 서랍 만들기)을 날리면 그건 buyer가
> 수수료를 냅니다. 그래서 SOL도 조금 받아둔 것이 헛수고는 아닙니다.

## 8. 온체인 확인은 왜 하나

**faucet이 "성공!"이라고 띄워도 그건 사이트의 주장일 뿐**입니다. 진짜 들어왔는지의
최종 근거는 항상 **블록체인 장부 직접 조회(온체인 조회)** 입니다. 블록체인의 철칙:
**"체인에 기록된 것만이 사실."**

조회 명령이 SOL/USDC가 다른 이유는 [7번](#7-돈이-2종류인-이유-sol-vs-usdc--관련-개념-총정리)의
저장 방식 차이 때문:

```bash
solana balance <주소> --url devnet                 # SOL (직접 담김)
spl-token accounts --owner <주소> --url devnet     # USDC (서랍에 담김)
```

`--url devnet`은 "어느 장부에 물어볼지" 지정. 같은 주소라도 mainnet/devnet은 별개
장부라, devnet에서 받은 건 devnet에 물어봐야 보입니다.

## 9. 서버가 로컬인데 키 공유가 의미 있나?

**"서버는 각자 로컬인데, 키 공유가 무슨 의미냐"** — 자주 나오는 오해입니다.
핵심은 **서버와 지갑은 있는 곳이 다르다**는 것.

|               | 로컬(내 PC)에 있음   | 블록체인에 있음(공유됨)          |
| ------------- | -------------------- | -------------------------------- |
| **API 서버**  | ✅ 각자 켬           | —                                |
| **지갑 · 돈** | — (내 PC엔 "열쇠"만) | ✅ Solana 위에 있어 전 세계 공유 |

- **API 서버**는 각자 자기 PC에서 켜니 공유 안 됨. 맞습니다.
- 하지만 **지갑·돈은 블록체인에 있습니다.** 내 PC엔 그 지갑을 여는 개인키만 있고요.

기술적으로 같은 buyer 개인키를 여러 환경에 넣으면 하나의 지갑을 함께 사용할 수
있지만, raw 개인키 파일을 팀원끼리 전달하는 방식은 권장하지 않습니다. 개발자는
각자 Devnet 지갑을 만들고 공개 주소만 공유하거나, 공용 실행 주체가 꼭 필요하면
Secret Manager·1Password 같은 비밀 관리 도구에서 접근 권한을 통제해야 합니다.

> **비유:** API 서버는 각자 집의 자판기이고 개인키는 결제 카드의 원본입니다.
> 카드번호가 아니라 카드 자체를 복제해 돌려쓰는 것과 같으므로 채팅·이메일로
> 전달하면 안 됩니다.

**결론: 같은 온체인 결과를 확인하는 데 개인키 공유는 필요하지 않습니다.** 각자
지갑으로 테스트해도 트랜잭션과 프로그램 상태는 같은 Explorer/RPC에서 확인할 수
있습니다.

**공용 서버(클라우드 배포)가 필요해지는 때:** 외부인에게 데모를 보일 때 /
프론트엔드가 API를 항상 호출할 때 / 24시간 서비스할 때. 그때 Docker로 클라우드에
올려 `https://...` 공개 주소를 만듭니다. **지금 개발 단계엔 로컬로 충분합니다.**

## 10. 그래서 뭐가 AI인가 — "AI 에이전트 빌드업"

**이 프로젝트의 정체를 가장 정확히 짚는 질문입니다. 솔직하게:**

> **지금 코드에는 AI가 없습니다.** 현재 `packages/agent/src/client.ts`는 "402 받으면
> → 서명 → 재시도"를 하는 **정해진 규칙대로 도는 자동 결제 봇**입니다. 스스로
> 판단하는 AI가 아닙니다.

그런데 왜 "AI 에이전트"라고 부르냐 — **AI가 나중에 쓸 수 있는 결제 손발을 먼저
만든 것**이기 때문입니다. 이 단계가 **"AI 에이전트 빌드업(build-up)"** 입니다.

```
[지금 = 우리가 만든 것: 손발]
  자동 결제 클라이언트 ──▶ x402 서버 ──▶ 결제

[다음 단계 = AI를 얹으면: 뇌]
  AI (LLM 등)
   "날씨 데이터가 필요하네"
   "이 API가 $0.001 받네, 예산 안이니 결제하자"   ← 여기가 AI의 판단
        │
        ▼
   우리 자동 결제 클라이언트 호출 ──▶ 결제 완료
```

**어디에 AI가 들어가나 (한눈에):**

| 구성요소                                          | 지금 상태     | AI인가                |
| ------------------------------------------------- | ------------- | --------------------- |
| API 서버 (`apps/api/`)                            | 완성          | ❌                    |
| 자동 결제 클라이언트 (`packages/agent/client.ts`) | 완성          | ❌ (자동 봇)          |
| **"언제 무엇을 살지" 판단하는 로직**              | **아직 없음** | ✅ **여기가 AI 자리** |

### 왜 이런 인프라가 필요한가

지금까지 결제는 **항상 사람**이 했습니다. AI는 카드번호도 없고, 은행이 "너 사람
맞아?" 하고 막아서 결제를 못 했죠. 하지만 AI 에이전트가 스스로 일하려면 "이 데이터
사자", "이 작업을 다른 AI한테 맡기고 수수료 내자"를 **사람 없이** 해야 합니다.

- **블록체인 지갑(개인키)** = AI도 가질 수 있는 지갑
- **x402** = 기계끼리 통하는 "돈 내면 API 열림" 규칙
- **소액 USDC** = $0.001씩 잘게 쪼갠 결제

이 셋을 합치면 **AI가 자기 지갑으로 API를 자동 결제**할 수 있고, 우리는 그 파이프라인을
devnet에서 증명했습니다. 폴더 이름이 `packages/agent/`인 것도 이 방향을 염두에 둔
것입니다.

### A2A — AI끼리 결제

더 나아가면 **AI가 다른 AI의 서비스를 사서 쓰는** 그림이 됩니다(Agent-to-Agent).
AI A가 "번역이 필요해" → AI B(번역 API)에게 x402로 $0.001 내고 결과를 받는 식.
사람이 낀 승인 없이 **기계 경제(machine economy)**가 도는 것 — x402가 지향하는
최종 그림이고, 우리 빌드업은 그 첫 벽돌입니다.

## 11. pay.sh는 뭐야? (왜 "간단"한가)

**pay.sh** = 터미널 명령을 감싸서 x402 결제를 자동 처리해주는 **CLI 도구**입니다.
Solana Foundation의 [`solana-foundation/pay`](https://github.com/solana-foundation/pay)
프로젝트로, 슬로건이 "Let your agents pay for any API"입니다.

**왜 간단하냐** — 기존 `curl` 앞에 `pay`만 붙이면 끝이기 때문입니다.

```bash
curl https://.../api/costly-data        # 그냥 하면 402로 실패
pay curl https://.../api/costly-data    # pay가 402 감지→지갑 승인→재시도까지 자동
```

동작 원리는 우리 `client.ts`와 **똑같습니다**(402 감지 → 서명 → 재시도). 차이는:

|         | 우리 `npm run client`             | pay.sh                                                                                         |
| ------- | --------------------------------- | ---------------------------------------------------------------------------------------------- |
| 형태    | 우리가 직접 짠 코드 (`client.ts`) | 설치해서 쓰는 범용 CLI                                                                         |
| 쓰는 법 | `npm run client`                  | 아무 `curl` 앞에 `pay`                                                                         |
| 특징    | 우리 프로젝트 전용                | curl·claude·codex 등 아무 명령이나 감쌈, MCP 서버 내장(AI assistant가 바로 유료 API 호출 가능) |

즉 pay.sh는 **"x402 결제를 코드 없이 터미널에서 범용으로" 쓰는 도구**이고, 우리는
학습·데모 목적상 **같은 걸 직접 코드로 구현**한 것입니다. 둘 다 지금 안 써도 되며,
pay.sh는 "이런 대안도 있다" 수준으로 알아두면 됩니다.

> ⚠️ README의 `npm install -g @solana/pay` 설치 명령은 부정확할 수 있습니다.
> `@solana/pay`(Solana Pay SDK)와 pay.sh는 별개일 수 있으니, 실제로 쓸 때는
> [pay.sh 설치 문서](https://pay.sh/docs/get-started/install)를 확인하세요.

## 12. 용어 사전 (부록)

| 용어                     | 한 줄 정의                                                  |
| ------------------------ | ----------------------------------------------------------- |
| **지갑 주소**            | 계좌번호. 공개해도 안전                                     |
| **개인키**               | 지갑을 여는 비밀번호+도장. 유출되면 돈 뺏김. 절대 공개 금지 |
| **시드 구문**            | 개인키를 12단어로 백업한 형태. 개인키와 같은 급 비밀        |
| **에어드랍**             | 코인을 지갑에 넣어주는 것 (여기선 테스트용 무료 배급)       |
| **faucet**               | 테스트 코인을 공짜로 뿌려주는 사이트(수도꼭지)              |
| **SOL**                  | Solana의 기본 화폐. 수수료를 이걸로 냄                      |
| **USDC**                 | 달러에 연동된 스테이블코인. 우리 상품값은 이걸로 냄         |
| **SPL 토큰**             | Solana 위에서 발행된 토큰(USDC 등). 이더리움 ERC-20에 해당  |
| **ATA (토큰 계정/서랍)** | 지갑이 특정 토큰을 담는 전용 하위 계정. 토큰 받으려면 필요  |
| **facilitator**          | 결제 검증·수수료 대납·정산을 대행하는 외부 서비스           |
| **온체인 조회**          | 블록체인 장부에 직접 물어 상태를 확인하는 것                |
| **devnet**               | Solana의 개발자 연습용 네트워크. 돈 가치 0                  |
| **x402**                 | HTTP 402 코드를 활용한 블록체인 결제 프로토콜               |
| **정산(settlement)**     | 결제 트랜잭션이 블록체인에 최종 기록되는 것                 |
| **A2A**                  | Agent-to-Agent. AI가 다른 AI 서비스를 사서 쓰는 것          |
