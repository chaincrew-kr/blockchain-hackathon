03

단계별 상세 — Input · Output · 필요 로직 · 결정사항

☐ 항목이 결정할 것. 권장안이 붙은 항목은 이견 없으면 그대로 채택한다. Phase 2 표시가 없는 개발 항목은 전부 Phase 1(7/29~8/1) 대상이다.

STAGE 0계약 온보딩 R3 R4 (UI) R1 (온체인 등록)

INPUT
가상 상영계약서 PDF — 문체부 「영화 상영 표준계약서」 양식 기반, 부율(서울 한국영화 5:5)·배급수수료 10%·MG·할인 처리 조항 + 의도된 충돌 1건
OUTPUT
승인된 정산 규칙 JSON(vN, SPEC §5 스키마) + 항목별 근거조항·원문·신뢰도 + 충돌 플래그 + 온체인 규칙 해시
필요 로직
  • Gemini Structured Output 호출 (스키마 강제, response_mime_type: application/json)
  • 충돌 검사: 비율 합계 ≠ 100% / 정산일 상호 불일치 / 할인 처리 기준 누락
  • 양측(배급·상영) 승인 상태머신 → 완료 시 init_escrow(rule_hash, ver) 호출
  • 추출 결과 캐시 (라이브 호출 실패 시 캐시 표시 — 데모 안전장치)
  • 사람 승인 UI — 추출 결과를 배급사·상영자 담당자가 확인·승인 (양측 승인 전 규칙 생성 불가)
  • 승인 규칙 온체인 기록 트랜잭션 — 승인 후엔 AI도 변경 불가, 개정은 신규 버전 발행으로만
결정할 것
  • 계약서에 MG 조항 포함 여부 — 권장: 포함하되 소액(예: MG 5,000). 워터폴 깊이를 보여주는 재료. 단 일정 밀리면 1순위 컷
  • 의도된 충돌의 종류 — 권장: "본문 45일 지급 vs 별지 30일 지급" 정산일 불일치 (화면에서 가장 직관적)
  • 승인 주체 — 권장: 배급·상영 양측 2인 승인 (단일 승인은 "AI가 멋대로" 반론에 취약)
  • 계약서 작성 담당·완료일 — R3, 7/29 중 초안 / 추출 스키마 필드는 7/29 중 packages/schema 확정
  • 문체부 표준계약서 다운로드 → 템플릿 확정 — 자동 접근 차단(robots)이라 수동 다운로드 필요. 상영 외 투자·배급 양식 포함 여부 확인 (MG·워터폴 조항 재료)

STAGE 1자금 유입 R4 R1 (deposit)

INPUT
시연자(관객 역할)의 티켓 구매 클릭 — 영화·회차·단가
OUTPUT
에스크로 PDA 입금 tx(Explorer 확인 가능) + 발권 이벤트 로그(회차·좌석·금액·시각) + 상태 Pending
필요 로직
  • 모의 티켓 구매 웹페이지 (React) — 실제 예매 사이트 UX, "결제하기" 버튼
  • Phantom 연동 → Solana Pay 결제 (수취 주소 = 영화별 에스크로 PDA)
  • 발권·환불 로그 적재 (STAGE 3 위험조정검증이 온체인에서 직접 읽는 원천 데이터)
  • 격리 불변식: Pending 자금의 유일한 출구 = 관객 환불
격리 성립 조건 (설계 불변식). ① 경유 계좌 0개 — 결제 수취 주소가 곧 에스크로 ② 수취 계정에 주인 없음 — PDA(개인키 부존재) ③ 미귀속(Pending) 자금은 전원 인출 불가, 유일한 출구는 관객 환불 ④ 결제의 즉시 최종성(USDC ~400ms). 이 넷이 갖춰질 때만 "결제 순간부터 격리"가 성립한다.
결정할 것
  • 데모 단가·건수 — 권장: 10 USDC × 3건 (STAGE 2 정산 계산과 원 단위 대조 가능한 규모)
  • 환불 데모 포함 여부 — 권장: 포함 (1건 환불 → Pending에서 관객 반환)
  • 티켓 영수증 온체인 발급 — 권장: 발권 로그+입금 tx로 갈음, 별도 영수증 계정은 컷 (계정 rent·복잡도 대비 효용 낮음)

STAGE 2배치 귀속 R1 R2 (집계 전달)

INPUT
Pending 총액 + 승인 규칙(vN) + STAGE 4의 "진행" 판정 + STAGE 3 정합성 검증 결과
OUTPUT
권리자별 Allocation 온체인 기록 (Claimable 전환 대기) — "누가 얼마 받을 자격인지"의 확정
필요 로직
  • settle_batch: 부과금(가액÷1.03×3%, 반올림) → VAT(잔액÷11) → 부율 분할 → 배급수수료 → MG 상환(잔액 추적) → 투자 상환 → 이익 배분
  • 불변식: Σallocated + reserved + disputed + refundable = gross_in
  • 규칙 버전 바인딩 — 어떤 입금에 어떤 vN이 적용됐는지 기록
  • 환불 처리 — Pending 중 환불은 관객 직접 반환 / 배치 후 환불은 Disputed 전환
결정할 것
  • 워터폴 구현 깊이 — 권장: 풀 구현 목표(수수료→MG→상환→배분), 지연 시 "수수료+단순 배분"으로 축소
  • 공제 계산 위치 — 온체인(프로그램 내) vs 오프체인 계산 후 결과만 기록 — 권장: 온체인. "코드가 규칙을 강제한다" 서사의 핵심. 반올림 산식은 u64 정수 연산으로 사전 검증 필수
  • 환불충당금(reserveRate) 포함 — 권장: 컷 (시간 남으면 슬라이드로만 설명)

STAGE 3위험조정검증 R2

INPUT
STAGE 1 온체인 발권·환불 로그 + 배치 트리거(P7) + 같은 상영관의 과거 정산 이력(온체인, 있으면)
OUTPUT
조정된 이상탐지 임계값 + 정합성 검증 결과(환불률·무료비율·발권초과·해시연속성 각각 통과/실패) + Phase 2 신뢰도 스코어 + Phase 2 증빙 대조 결과
필요 로직
  • 과거 이력 조회 — 같은 상영관의 이전 정산 배치 기록을 온체인 RPC로 조회(무료), 정산 규모·이상탐지 이력·분쟁 이력 집계
  • 임계값 조정 — 이력 없는 신규 상영관은 기본(보수적) 임계값, 이력 좋은 상영관은 정상 임계값 적용
  • 정합성 검증 4종 실행: 환불률>10%(P3), 무료비율>15%(P3), 발권수>좌석수(P4), 해시 불연속성(P5) — STAGE 1 로그에서 직접 계산, 외부 데이터 불필요
Phase 2 — Phase 1 완주 후 추가 (x402 두 곳)
  • checkTrustFreshness() 훅: 이력이 없거나 오래됐으면(P1) 신뢰도 조회 API를 x402로 구매(P2 예산 확인 후) → 임계값 조정에 반영
  • checkRefundEvidence() 훅: 환불 수치 불일치가 발견되고 금액·불일치 정도가 기준을 넘으면(P9) 증빙 API를 x402로 구매 → 대조해 일치하면 오탐 처리(정산 진행), 불일치 확정 시 보류 유지
  • 두 훅 모두 Phase 1에서는 항상 {needed:false}를 반환하는 no-op으로 구현하고, Phase 2에서 내부 로직만 채워 넣는다 (SPEC §7 삽입 지점 참조)
결정할 것
  • Phase 2 결제 스택 — pay.sh 채택 (확정 권장) — 공식 심사 기준 "인프라 연동"에 USDC·Solana Pay·pay.sh가 명시됨. pay.sh는 x402·MPP 동시 지원 — 반복 조회는 MPP 세션 적합성을 발표에서 언급, 데모는 x402 단건으로 충분
  • 임계값 조정 폭 — 권장: 신규 상영관은 정상 대비 더 엄격하게(예: −30%) — 정확한 수치는 합의 필요
  • 배치 트리거의 데모 구현 — 실제 Scheduler 대기 vs "정산일 도래" 버튼 — 권장: 버튼(시연 통제) + Scheduler는 코드로 존재 증명. "데모에서는 시간을 압축합니다" 1문장 선언

STAGE 4정산 실행 판단 R2 R3 (프롬프트)

INPUT
STAGE 3 검증 결과(조정된 임계값 + 정합성 검증 + Phase 2 신뢰도/증빙) + 회차 메타(좌석수·평균 점유율·과거 환불률)
OUTPUT
회차·금액 단위의 "진행 / 부분 보류" 판정 + 근거 조항·적용 정책·에이전트 권한 범위(지급 의도) + Gemini 자연어 근거 리포트
필요 로직
  • STAGE 3 결과 종합 → 진행 vs 부분 보류 최종 판정 확정
  • Gemini 패턴 추론 — 임계 미달이어도 이상한 패턴(예: 심야 회차 점유율 급등) 플래그
  • 판정 로그를 자연어로 저장·화면 노출 (룰베이스로 보이면 AI 감점)
  • 보류 → mark_disputed(amount), 정상 → STAGE 2 진행
AI 심사 감점 주의. 화면에 "보류됨"만 뜨면 룰베이스 if문으로 보인다. 반드시 왜 보류했는지를 Gemini가 생성한 자연어로 보여줄 것. 분쟁의 본질(부율이 아니라 베이스 금액의 애매함 — 할인·환불·초대권의 유효매출 포함 여부)을 잡아내는 것이 이 판단의 존재 이유다.
결정할 것
  • 데모용 이상 시나리오 1개 확정 — 권장: "무료초대권 비율 초과" (계약 조항→탐지→보류가 한 줄로 연결: "제5조 무료 발권 상한 5% 대비 18% 발권"). 대안: 환불률 급증
  • 임계값 최종 수치 — 권장: P3=10%/15%, P4=좌석수, 그대로 확정 (계약서 조항과 숫자 일치시킬 것)
  • Gemini 패턴 추론의 데모 포함 — 권장: 포함하되 리허설에서 출력 불안정하면 룰+Gemini "설명 생성"으로 축소

STAGE 5분배 실행 R1

INPUT
Allocated 금액 + 계약상 지급일 도달(데모: 버튼) + STAGE 4 판정
OUTPUT
극장·배급·제작·투자 지갑 동시 입금 tx(원자적) / Disputed 잔류분 / 부정 인출 거부 tx
필요 로직
  • 다자 원자 분배 — 전부 성공 or 전부 롤백 (자체 다중 송금 instruction 기본)
  • claim: 요청자 Claimable 잔액 초과분 온체인 거부 (데모 클라이맥스)
  • 분쟁 해결: resolve_dispute(approve) → 지급 또는 환수
결정할 것
  • 분배 방식 — MPP 연동 vs 자체 다중 송금 instruction — 권장: 자체 구현 기본 + MPP는 시간 되면 스파이크로 타진 (외부 의존성 리스크)
  • 부정 인출 데모의 행위자 — 권장: "상영자 지갑이 전액 인출 시도"
  • 분쟁 해결 장면 포함 — 권장: 보류까지만 데모, resolve는 대시보드 버튼 존재로만 표시 (데모 영상 러닝타임 유지)

STAGE 6투명 대시보드 R4 R2 (로그 API) R3 (KOBIS)

INPUT
온체인 상태(RPC) + 오프체인 판단 로그(Firestore) + KOBIS 오픈API
OUTPUT
상태머신 현황 · 권리자별 잔액 · tx 타임라인 · 이상탐지 리포트 · KOBIS 대조 패널
필요 로직
  • 에스크로 계정 구독/폴링 → 상태 시각화 (Pending→…→Paid/Disputed)
  • tx 항목마다 Explorer 링크
  • KOBIS 일별 박스오피스 호출 — 실존 독립영화 1편 병렬 표시 ("실데이터 연동" 증명)
결정할 것
  • KOBIS 패널 포함 — 권장: 포함 (실데이터 서사)
  • 신뢰도 스코어(FR-24, 자체 산출) — 권장: 컷. 슬라이드 목업 1장으로 대체
  • 대조용 실존 독립영화 선정 — R3가 7/30까지 KOBIS에서 상영 중인 독립·예술영화 1편 선정
