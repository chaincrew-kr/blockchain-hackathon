# Product Brief — 독립영화 온체인 정산 에이전트

> 이 문서는 제품을 빠르게 이해하기 위한 요약본입니다. 상세 요구사항·기술 설계·역할과
> 일정은 각각 `REQ-INDIE-001 v0.2`, `SPEC-INDIE-002 v0.5`,
> `PLAN-INDIE-003 v0.4`를 기준으로 합니다.

## 한 줄 설명

영화 티켓 매출을 발생 순간부터 영화별 온체인 에스크로에 격리하고, AI 에이전트가
승인된 계약 규칙과 발권 이력을 검증해 정상 금액은 자동 정산하고 이상 금액만
보류하는 B2B 정산 인프라입니다.

## 문제

영화 티켓 매출은 극장 운영사나 예매 사업자에게 먼저 모인 뒤 권리자에게 사후
정산됩니다. 중간 사업자에게 유동성 문제나 회생·파산이 발생하면 이미 판매된 표의
배급사·제작사·투자자 몫까지 운영자금과 함께 묶일 수 있습니다.

기존 정산은 계약 해석, 매출 대조, 공제 계산과 지급이 수작업으로 분리되어 있어
처리가 느리고 오류나 분쟁의 원인을 추적하기 어렵습니다. 이상 한 건 때문에 전체
정산이 멈추는 문제도 있습니다.

## 대상 사용자

- 독립·예술영화 전용관
- 영화제와 비상설·공동체 상영 조직
- 배급사, 제작사, 투자자 등 정산 권리자
- 계약과 지급 상태를 검토하는 운영 담당자

관객용 암호화폐 서비스가 아닙니다. 상용 환경에서 관객은 기존처럼 원화로
결제하고, 제품은 그 뒤의 사업자 간 정산 구간을 바꿉니다. 해커톤 데모에서는 핵심
메커니즘을 증명하기 위해 시연자가 Solana Devnet USDC로 직접 결제합니다.

## 해결 방식

1. Gemini가 계약서에서 부율·수수료·MG·공제·정산일을 근거 조항과 함께 구조화해
   추출합니다.
2. 배급사와 상영자 양측이 결과를 승인하면 규칙 해시와 버전을 온체인에 고정합니다.
3. 티켓 결제금이 개인키가 없는 영화별 에스크로 PDA로 직접 들어가 운영자금과
   분리됩니다.
4. 정산 에이전트가 회차별 발권·환불 입력, 과거 상영관 이력과 온체인 계정 상태를
   바탕으로 환불률, 무료 발권 비율과 좌석 초과를 검증합니다.
5. 정상 금액은 승인된 결정론적 규칙으로 귀속·분배하고, 이상 금액만
   `Disputed`로 보류합니다.
6. Gemini가 판단 근거와 관련 계약 조항을 자연어 리포트로 설명합니다.
7. 대시보드에서 상태, 권리자별 잔액, 트랜잭션과 보류 사유를 확인합니다.

## 현장 검증

2026년 7월 씨네큐브 실무 답변을 통해 영화·상영일·회차별 관객 수와 매출, 개별
거래의 유료·무료·할인·환불 여부가 발권 시스템에서 구분된다는 점을 확인했습니다.
극장은 Excel로 데이터를 추출할 수 있고 발권 솔루션 업체는 API 제공도 가능한
것으로 파악됐습니다.

반면 해당 극장의 KOBIS 전송은 상영일 다음 날 새벽 일 1회 일괄 방식이었고,
할인·쿠폰을 반영한 유효매출 산정 기준은 극장마다 다를 수 있다는 답변을
받았습니다. 이는 KOBIS를 실시간 정산 원장으로 가정하거나 유효매출 규칙을 하나로
고정하면 안 된다는 뜻입니다.

따라서 실서비스에서는 극장 Excel 또는 발권 솔루션 API를 원천 입력으로 정규화하고,
KOBIS는 익일 사후 대조에 활용합니다. 유효매출은 영화별 승인 계약 규칙으로 다시
계산합니다. 자세한 조사 내용과 한계는
[씨네큐브 발권·정산 실무 답변](research/CINECUBE_FIELD_RESPONSE_2026-07-31.md)에
정리했습니다.

## 설계 원칙

- AI는 돈을 임의로 나누지 않습니다.
- 분배는 사람이 승인한 버전별 결정론적 규칙이 실행합니다.
- AI는 계약 규칙 생성과 집행 전 검증·이상 탐지를 담당합니다.
- 승인된 규칙은 AI를 포함한 누구도 수정할 수 없으며 개정은 새 버전으로만
  발행합니다.
- 각 권리자는 자기 `Claimable` 잔액까지만 인출할 수 있습니다.
- 이상이 발생해도 정상 금액의 지급은 중단하지 않습니다.
- 모든 지급은 규칙 버전, 입력 데이터 해시와 계산 결과로 재검증할 수 있어야
  합니다.

## MVP 범위

### Phase 1 — 필수

- 가상 계약서 업로드, Gemini 구조화 추출, 충돌 탐지와 양측 승인
- Phantom 지갑 서명 기반 Devnet USDC 결제와 에스크로 Vault 직접 유입
- 온체인 규칙 버전·자금 상태와 오프체인 회차별 발권·환불 입력 연결
- 위험조정검증과 진행·부분 보류 판정
- 정상분의 권리자별 Allocation 귀속과 이상분 격리
- 자기 몫 초과 인출의 온체인 거부
- 상태·잔액·트랜잭션·판정 근거 대시보드

### Phase 2 — Phase 1 완주 후

- 신규·이력 만료 상영관의 외부 신뢰도 조회
- 환불 불일치 발생 시 외부 증빙 조회
- 에이전트가 정책과 예산을 확인한 뒤 x402/pay.sh로 조건부 구매

Phase 2는 상시 경로가 아니며 현재 MVP에는 구현하지 않았습니다. Phase 1은 별도의
유료 증빙 API 구매 없이 승인 계약, 정규화한 발권·환불 데이터, Solana 계정 상태와
KOBIS 사후 대조로 실행합니다.

## 현재 구현 상태

- Web과 정산 Agent를 Google Cloud Run에 배포하고 API 키·Agent 키는 Secret
  Manager로 분리했습니다.
- Solana Devnet에서 실제 `settle_batch` 2건과 `mark_disputed` 4건을 실행했습니다.
- 별도 연습 Escrow에서 정상 Claim, 초과 인출 거부, 분쟁 중 인출 거부와 해제 후
  Claim을 확인했습니다.
- Agent 42개, AI Data 4개, Devnet Seed 3개로 총 49개 자동 검사를 통과했습니다.
- 대시보드 일부 잔액·상태는 데모 스냅샷을 사용하며, x402/pay.sh와 원화 PG 연동은
  후속 범위입니다.

전체 흐름, 화면과 구현 근거는 [제출용 HTML 보고서](e2e/ChainCrew_Hackathon_Submission.html)와
[PDF 보고서](e2e/ChainCrew_Hackathon_Submission.pdf)에 정리했습니다.

## 데모 성공 기준

- 계약서의 근거 조항·신뢰도와 의도된 충돌 한 건이 표시되고, 양측 승인 후 규칙
  해시가 온체인에 기록된다.
- 관객 역할 지갑의 결제 세 건이 에스크로 PDA에 직접 유입되고 Explorer에서
  확인된다.
- 티켓별 공제와 권리자 몫이 정확히 계산된다.
- 에이전트가 사람 개입 없이 이력 조회, 임계값 조정, 정합성 검증과 정산 판단을
  수행한다.
- 주입된 이상 금액만 보류되고 정상 금액은 지급되며, 자연어 보류 리포트가
  생성된다.
- 타인의 몫을 포함한 초과 인출 시도가 온체인에서 거부된다.
- 전체 과정의 상태와 트랜잭션 링크가 대시보드에 표시된다.
