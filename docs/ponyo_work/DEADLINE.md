### 8/3은 파이널이 아니다 — 전략이 달라진다

8/3 제출물로 **10팀을 선정**하고, 뽑힌 팀은 8/21 데모데이까지 디벨롭 기간을
받는다. 즉 8/3에 필요한 것은 **완성도가 아니라 "이 팀은 될 것 같다"는 확신**이다.

이 구분이 우선순위를 바꾼다.

| 8/3까지 필요한 것                        | 8/21까지 미뤄도 되는 것          |
| ---------------------------------------- | -------------------------------- |
| 온체인이 **실제로 돈다**는 증거 (tx 1건) | instruction 7개 전부             |
| 부분 보류라는 **차별점**이 보이는 장면   | Gemini 자연어 리포트 품질        |
| 재현 가능한 Repo·README                  | 라이브 URL, Cloud Scheduler      |
| 문제 정의와 아키텍처가 설득되는 소개서   | 대시보드 완성도, KOBIS 대조 패널 |

**심사위원이 8/3에 확인하는 건 "완성됐나"가 아니라 "핵심 메커니즘이 진짜
작동하나"다.** 온체인 tx가 단 한 건이라도 Explorer에 남아 있는 것과 stub만
있는 것의 차이가 결정적이고, 그 외 항목은 디벨롭 기간에 채울 수 있다.

## 2. 역산 논리

필수 제출물 3번이 모든 것을 결정한다.

> **데모 영상 (3분 이내) — 실제 온체인 결제 전 과정**

영상을 찍으려면 그 앞의 것들이 순서대로 필요하다.

```
데모 영상 촬영
  ← E2E가 최소 1회 성공 (Devnet 실제 tx)
    ← A 구매웹 · B·C 프로그램 · D 에이전트 연결
      ← IDL 공유 (packages/schema/idl)
        ← instruction 구현
          ← 계정 구조(state.rs) 확정   ← 지금 여기서 막혀 있음
```

계정 구조는 실행계획서상 **7/29 싱크 체크포인트**였고 하루 지났다. 현재
`programs/movie_escrow/src/state.rs`는 첫 줄이 "논의 시작용 초안"이고
instruction 7개가 전부 `NotImplemented`, `packages/schema/idl`에는 README만 있다.

## 4. 포기 판정 기준

시간이 부족할 때 무엇을 먼저 버릴지 미리 정해두면 당일에 흔들리지 않는다.

| 시점        | 상황                 | 결정                                                        |
| ----------- | -------------------- | ----------------------------------------------------------- |
| 7/31(금) 밤 | IDL 없음             | 환불·분쟁해결 instruction을 컷, 5개 최소 경로로 축소        |
| 8/1(토) 낮  | Devnet 불안정        | **Localnet으로 전환** — 영상에 "로컬 검증넷" 명시           |
| 8/1(토) 밤  | 온체인 tx 여전히 0건 | 최후 수단: stub 영상 + "체인 연동 진행 중" 명시 (감점 감수) |
| 상시        | 라이브 URL 미배포    | 포기 — 권장 항목이고 디벨롭 기간에 채우면 된다              |
| 상시        | Gemini 리포트 미연결 | 템플릿 문구로 제출 — 디벨롭 기간에 교체                     |

라이브 URL과 Gemini는 8/3에 없어도 된다. **10팀에 들면 8/21까지 채울 시간이
있다.** GCP 결제 계정([#13](https://github.com/chaincrew-kr/blockchain-hackathon/issues/13))이
막혀 있으면 그대로 두고 온체인 연결에 자원을 몰아주는 게 맞다.

반대로 **온체인 tx 0건은 디벨롭 기간으로 미룰 수 없다.** 그게 없으면 애초에
10팀에 들 근거가 약하다.

## 5. 데모 최소 경로 — 꼭 필요한 instruction만

instruction 7개를 다 만들 시간이 없다면, 영상 시나리오에 실제로 등장하는 것만
먼저 만들면 된다.

| instruction       | 필요 | 영상에서의 역할                         |
| ----------------- | ---- | --------------------------------------- |
| `init_escrow`     | ✅   | 규칙 해시 온체인 등록 (STAGE 0 마무리)  |
| `deposit`         | ✅   | 관객 결제가 에스크로로 직접 유입        |
| `settle_batch`    | ✅   | 정상 회차 귀속 확정                     |
| `mark_disputed`   | ✅   | 이상 회차만 격리 — **제품의 핵심 장면** |
| `claim`           | ✅   | 권리자 인출 + 초과 인출 거부 (REQ D6)   |
| `refund_pending`  | ⬜   | 환불 데모는 실행계획서에서 "권장"       |
| `resolve_dispute` | ⬜   | 보류 해제는 영상 3분에 안 들어간다      |

**5개면 필수 제출물의 데모 영상을 찍을 수 있다.** 뒤의 2개는 코드가 존재한다는
것만 보여주고 시연에서는 빼도 된다.

## 6. 지금 D가 할 수 있는 것 / 없는 것

D 파트는 stub 기준으로 완주해 있어서(테스트 29개 통과, 컨테이너 동작 확인)
**IDL이 오는 즉시 붙이면 되는 상태**다. `ChainGateway`·`HistoryProvider`를
인터페이스로 분리해 둔 이유가 이것이다.

- **D가 못 하는 것:** 계정 구조 확정, instruction 구현, Devnet 배포 → B·C 영역
- **D가 지금 하는 것:** [TASKS.md](TASKS.md)의 T4~T6 — 픽스처 확대, Gemini 연동,
  Anchor 게이트웨이 골격을 미리 짜서 IDL 도착 시 연결 시간을 줄이는 작업

⚠️ **주의:** D의 현재 결과물은 `STUB_SETTLE_…` 같은 **가짜 트랜잭션 서명**을
반환한다. Explorer에 아무것도 남지 않으므로 이 상태로는 "실제 온체인 결제
전 과정"을 촬영할 수 없다.
