# 4인 팀 작업 계획

## 역할

| 담당                | 주 작업 경로          | 첫 산출물                                               |
| ------------------- | --------------------- | ------------------------------------------------------- |
| 1. Blockchain       | `packages/blockchain` | Devnet 판매자/구매자 지갑, USDC 확보, 정산 검증         |
| 2. AI / Agent       | `packages/agent`      | 자동 결제 호출, 도구 선택 로직, A2A 인터페이스          |
| 3. Backend/Cloud    | `apps/api`, Docker    | 유료 API, 오류/로그, 클라우드 배포 URL                  |
| 4. Frontend/Product | `apps/web`, `docs`    | 결제 흐름 UI, 제품 설명서 초안, 데모 시나리오/영상 편집 |

제품 설명과 데모 영상은 4번 담당자가 취합하되, 각 담당자는 자기 영역의 30초 분량
화면/설명과 실패 대응 내용을 제공합니다.

## 3단계 마일스톤

### M1 — 연결

- API가 결제 없이 402를 반환한다.
- 구매자 Devnet 지갑과 판매자 Devnet 지갑을 분리한다.
- 클라이언트가 결제 후 JSON을 받는다.
- Docker 한 명령으로 API가 뜬다.

### M2 — 제품

- 실제 유료 데이터/AI 작업 하나를 `costly-data` 대신 연결한다.
- 에이전트가 가격을 확인하고 예산 안에서 결제한다.
- UI가 요청→402→결제→결과→Explorer 링크를 보여준다.
- 결제 실패, 잔액 부족, 퍼실리테이터 장애를 처리한다.

### M3 — 제출

- `dev` 통합 및 E2E 리허설 후 `dev → main` 릴리스 PR을 만든다.
- 제품 설명서, 아키텍처 그림, 2~3분 데모 영상을 완성한다.
- mainnet 키는 사용하지 않고 Devnet임을 화면과 문서에 명시한다.

## 병렬 작업 규칙

- 각 담당자는 자기 경로를 기본 소유하고 공용 파일 변경은 PR 설명에 표시합니다.
- API 계약은 `docs`에 먼저 적고 프론트/에이전트가 같은 계약을 사용합니다.
- 하루 한 번 `dev`를 자기 브랜치에 병합하거나 rebase해 통합 충돌을 조기에 찾습니다.
- 데모 직전에는 기능 추가를 멈추고 실패 복구와 재현성만 확인합니다.
