# 씨네큐브 발권·정산 실무 답변 정리

> 조사일: 2026-07-31  
> 조사 방식: 씨네큐브 홈페이지 1:1 문의 후 실무자 이메일 답변  
> 문서 성격: 제품 가설 검증을 위한 1개 극장 사례  
> 개인정보 보호: 메일 주소와 화면 캡처는 저장소에 포함하지 않고 답변 내용만
> 요약한다.

## 1. 조사 목적

독립영화관의 실제 발권 데이터 구조, 영화관입장권통합전산망(KOBIS) 전송 방식,
정산 기준을 확인하기 위해 다음 내용을 문의했다.

- 영화·상영일·회차 단위로 관객 수와 매출을 구분할 수 있는지
- 유료, 할인, 무료 초대, 환불·취소 거래를 구분할 수 있는지
- 개인정보를 제외한 데이터를 Excel·CSV·API로 추출할 수 있는지
- KOBIS 전송 주기와 전송 주체
- 정산이 실제 유효매출을 기준으로 하는지
- 표준계약과 영화별 개별계약 중 무엇을 사용하는지

## 2. 답변에서 확인된 사실

### 발권 데이터

- 영화별, 상영일별, 회차별 관객 수와 매출이 구분되어 저장된다.
- 개별 거래에서 유료·무료 여부, 할인 여부, 환불 여부를 확인할 수 있다.
- 극장에서는 발권 데이터를 Excel 형식으로 추출할 수 있다.
- 답변자의 이해로는 발권 솔루션 업체가 API 형태의 데이터 제공도 지원할 수 있다.

### KOBIS 전송

- 해당 극장의 발권 정보는 하루 한 번 KOBIS로 전송된다.
- 전송 시점은 상영일 다음 날 새벽이며 일괄 전송 방식이다.
- 전송은 극장 직원의 수작업이 아니라 발권 솔루션 시스템이 대행한다.

### 정산

- 티켓 정산은 유효매출을 기준으로 한다.
- 할인·쿠폰 정책의 경우의 수가 많아 유효매출 산정 기준은 극장마다 다를 수 있다.
- 극장과 배급사의 상영계약은 일반적으로 표준계약을 따르지만, 영화별 별도계약을
  체결하는 경우도 있다.

## 3. 우리 제품 가설과의 관계

| 기존 가설                                      | 현장 답변                              | 판단                     |
| ---------------------------------------------- | -------------------------------------- | ------------------------ |
| 영화·회차별 매출 검증이 가능하다               | 영화·상영일·회차별 저장                | 지지됨                   |
| 무료·할인·환불을 별도로 검증해야 한다          | 개별 거래별 구분 가능                  | 강하게 지지됨            |
| API로 발권 데이터를 받을 수 있다               | 극장은 Excel, 솔루션 업체는 API 가능성 | 부분 지지·추가 확인 필요 |
| KOBIS 데이터를 실시간 정산 입력으로 쓸 수 있다 | 해당 극장은 익일 새벽 일괄 전송        | 수정 필요                |
| 유효매출 계산 규칙을 하나로 고정할 수 있다     | 할인·쿠폰 정책에 따라 극장별 차이      | 기각됨                   |
| 표준계약 하나로 모든 영화를 처리할 수 있다     | 영화별 별도계약 가능                   | 기각됨                   |

이 답변은 제품의 핵심 문제를 강화한다. 원천 데이터에는 무료·할인·환불 정보가
존재하지만, **어떤 거래를 유효매출에 포함할지는 계약과 극장 정책에 따라
달라진다.** 따라서 데이터 집계만으로 정산이 자동으로 결정되지 않으며, 영화별로
승인된 규칙을 데이터와 연결하는 계층이 필요하다.

## 4. 설계에 반영할 사항

### 데이터 수집 계층

실서비스 입력은 하나로 고정하지 않고 어댑터 구조로 둔다.

```text
초기 도입: 극장 Excel 내보내기
    ↓ 정규화
공통 TicketEvent 스키마
    ↑ 정규화
확장 도입: 발권 솔루션 업체 API
```

- MVP 또는 파일럿은 Excel 업로드로도 검증할 수 있다.
- API 연동은 발권 솔루션 업체와 필드·인증·제공 조건을 별도로 확인해야 한다.
- Excel과 API가 같은 공통 이벤트로 변환되는 계약 테스트가 필요하다.

### KOBIS의 역할

KOBIS는 외부 집계·대조 데이터로 사용하고 정산 트리거의 유일한 실시간 원천으로
가정하지 않는다.

```text
극장 발권 원장/솔루션 API → 회차 종료 후 정산 입력
KOBIS 익일 집계          → 사후 대조·불일치 탐지
```

해당 극장 사례에서는 익일 전송이므로 관객 결제 직후 자금 분리와 회차 종료 정산을
KOBIS 응답에 의존시키면 지연이 발생한다.

### 계약 규칙

- `SettlementRule`은 영화별 버전으로 유지한다.
- 할인·쿠폰·무료 발권의 유효매출 포함 여부를 규칙으로 표현해야 한다.
- “무료 발권 비율”과 “유효매출에서 제외되는 거래”를 같은 개념으로 취급하지
  않는다.
- 표준계약 기본값을 제공하더라도 영화별 특약이 우선 적용되어야 한다.

### 발권 이벤트 스키마

현재 `TicketEvent`의 `kind`, `amount`, `seat`만으로 유료·무료와 환불 일부는 표현할
수 있지만 할인·쿠폰의 원인과 유효매출 반영 근거는 남기기 어렵다. 다음 필드를
공통 스키마 후보로 검토한다.

```ts
interface TicketEventCandidate {
  transactionId: string;
  ticketType: "paid" | "complimentary";
  discountType?: "coupon" | "membership" | "promotion" | "other";
  listPrice: number;
  paidAmount: number;
  settlementEligibleAmount: number;
  refundOfTransactionId?: string;
  source: "excel" | "ticketing-api" | "demo";
}
```

필드명과 필수 여부는 A·B·D 리뷰 후 `packages/schema`에 반영한다. 특히
`settlementEligibleAmount`를 원천 시스템이 제공하는 값으로 신뢰할지, 승인된
계약 규칙으로 우리 시스템이 다시 계산할지는 별도 결정이 필요하다.

## 5. 데모와 발표에 사용할 수 있는 근거

> 독립영화관 현장 답변을 통해 영화·상영일·회차별 매출과 개별 거래의
> 유료·무료·할인·환불 여부가 발권 시스템에 구분되어 있다는 점을 확인했다.
> 그러나 유효매출 산정은 극장 정책과 영화별 계약에 따라 달라질 수 있고,
> KOBIS 전송도 해당 극장에서는 익일 일괄 방식이었다. 그래서 우리는 단순 매출
> 집계가 아니라, 원천 발권 데이터를 영화별 승인 규칙과 자금 집행에 연결하는
> 시스템을 설계했다.

“모든 영화관이 동일한 방식으로 운영된다”거나 “모든 발권 업체가 API를 제공한다”는
주장에는 이 자료를 사용하지 않는다.

## 6. 추가 확인이 필요한 질문

- Excel 실제 컬럼명과 익명 샘플을 받을 수 있는가?
- 발권 솔루션 API의 제공 업체, 인증 방식, 호출 주기와 비용은 무엇인가?
- 할인·쿠폰별 유효매출 산식은 누가 설정하고 어디에 저장하는가?
- 환불은 원거래 ID와 연결되는가, 별도 음수 거래로 저장되는가?
- KOBIS 전송 실패·재전송·사후 수정은 어떻게 처리되는가?
- 배급사 정산서와 발권 원장의 대조 키는 무엇인가?
- 영화별 특약이 표준계약보다 우선하는 항목은 주로 무엇인가?

## 7. 증거의 한계

- 씨네큐브 한 곳의 답변이므로 전체 독립영화관으로 일반화할 수 없다.
- API 제공 여부는 답변자가 “그렇게 알고 있다”고 표현한 간접 정보다.
- 실제 Excel 컬럼, API 명세, 정산서와 계약서는 확인하지 못했다.
- 유효매출의 구체적인 산식은 극장별로 다르다는 수준까지만 확인됐다.

따라서 이 자료는 제품 방향과 추가 조사 우선순위를 정하는 정성적 근거로 사용하고,
정확한 데이터 계약은 원본 샘플과 발권 솔루션 API 명세를 받은 뒤 확정한다.
