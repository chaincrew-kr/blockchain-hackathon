# 독립·예술영화관 현장 조사 종합

> 조사 기간: 2026년 7월  
> 조사 방식: 홈페이지 1:1 문의 및 이메일 서면 답변  
> 응답 대상: 씨네큐브, 서울아트시네마  
> 문서 성격: 제품 가설 검증을 위한 정성 조사이며 통계 표본이 아닙니다.

답변자의 이름, 이메일 주소와 회신 화면은 공개하지 않고 제품 설계에 필요한
극장명과 답변 내용만 정리했습니다.

## 무엇을 물었나

1. 영화·상영일·회차별 관객 수와 매출을 구분할 수 있는가
2. 유료·할인·무료 초대·환불 거래를 구분할 수 있는가
3. 개인정보를 제외한 발권 데이터를 Excel·CSV·API로 추출할 수 있는가
4. KOBIS 전송 주기와 전송 주체는 무엇인가
5. 실제 정산이 어떤 유효매출과 계약을 기준으로 이루어지는가

## 두 극장의 답변에서 확인한 것

| 확인 항목              | 씨네큐브                                     | 서울아트시네마 | 제품 판단                      |
| ---------------------- | -------------------------------------------- | -------------- | ------------------------------ |
| 발권 데이터 Excel 추출 | 가능                                         | 가능           | 초기 파일럿 입력으로 활용 가능 |
| KOBIS 전송 시점        | 상영일 다음 날 새벽 일괄                     | 실시간 자동    | 극장별 차이가 있음             |
| KOBIS 전송 주체        | 발권 솔루션 시스템                           | 시스템 자동    | 수작업보다 시스템 연동 문제    |
| 거래별 상세 구분       | 유·무료, 할인과 환불 여부 확인 가능          | 추가 확인 필요 | 공통 스키마 검증 필요          |
| 유효매출 기준          | 할인·쿠폰 정책에 따라 극장마다 다를 수 있음  | 추가 확인 필요 | 하나의 고정 계산식 사용 불가   |
| 계약 형태              | 표준계약이 일반적이나 영화별 별도계약도 존재 | 추가 확인 필요 | 영화별 규칙 버전과 승인이 필요 |
| 발권 솔루션 API        | 업체 지원 가능성에 대한 간접 답변            | 추가 확인 필요 | 실제 업체 명세 확인 전 미확정  |

두 곳의 KOBIS 전송 시점이 서로 달랐다는 사실이 중요합니다. 통합전산망에 같은
종류의 데이터를 보내더라도 현장 반영 시점은 같지 않았습니다. 따라서 MovieEscrow는
KOBIS를 결제 직후 정산을 시작하는 유일한 실시간 원장으로 사용하지 않습니다.

## 제품 가설이 어떻게 바뀌었나

| 처음 가정                                  | 현장 답변                                 | 반영 결과                             |
| ------------------------------------------ | ----------------------------------------- | ------------------------------------- |
| KOBIS를 실시간 정산 입력으로 쓸 수 있다    | 익일 일괄과 실시간 자동 전송이 함께 존재  | KOBIS는 사후 대조·불일치 탐지에 사용  |
| 유효매출 계산 규칙을 하나로 고정할 수 있다 | 할인·쿠폰 기준은 극장마다 다를 수 있음    | 영화별 `SettlementRule`을 버전 관리   |
| 표준계약 하나로 모든 영화를 처리할 수 있다 | 영화별 별도계약이 존재할 수 있음          | 양측 승인과 영화별 특약 우선 적용     |
| 발권 검증에 필요한 원천 데이터가 부족하다  | 거래 데이터와 Excel 추출 기능이 이미 존재 | Excel/API 어댑터로 기존 시스템과 연결 |

기각된 가설이 오히려 제품의 필요성을 분명하게 했습니다. 원천 데이터가 없는 것이
아니라, **서로 다른 원천 데이터를 영화별로 승인된 계약 규칙과 실제 자금 집행에
연결하는 계층**이 없었습니다.

## 설계 반영

### 입력 어댑터

```text
초기 도입: 극장 Excel 내보내기
                 ↓ 정규화
          공통 TicketEvent 스키마
                 ↑ 정규화
확장 도입: 발권 솔루션 업체 API
```

- 파일럿은 개인정보를 제거한 Excel로 시작할 수 있습니다.
- API는 발권 솔루션별 필드, 인증, 호출 주기와 비용을 확인한 뒤 연결합니다.
- Excel과 API가 같은 `TicketEvent`를 만드는지 계약 테스트로 확인합니다.

### KOBIS의 역할

```text
극장 발권 원장 / 솔루션 API → 회차 종료 후 정산 입력
KOBIS 집계                   → 사후 대조 · 불일치 탐지
```

### 영화별 계약 규칙

- 할인·쿠폰·무료 발권의 유효매출 포함 여부를 영화별 규칙으로 명시합니다.
- 표준계약을 기본값으로 제공하되 영화별 특약을 우선합니다.
- 변경 전후의 규칙 버전과 적용 회차를 구분합니다.

## 추가 확인이 필요한 것

- 개인정보를 제거한 실제 Excel 컬럼과 샘플
- 발권 솔루션 API의 인증, 호출 주기, 비용과 환불 연결 방식
- 할인·쿠폰별 유효매출 산식의 설정 주체와 저장 위치
- KOBIS 전송 실패, 재전송과 사후 수정 처리 방식
- 정산 확인·대사에 드는 시간과 정산금 수령 기간

## 해석의 한계

- 두 극장의 서면 답변이므로 전체 독립영화관으로 일반화하지 않습니다.
- API 제공 여부는 간접 답변이며 실제 API 명세는 확인하지 못했습니다.
- 서울아트시네마는 KOBIS 전송 방식과 Excel 추출 가능 여부를 중심으로
  답변했으므로 나머지 항목은 추가 조사가 필요합니다.
- 정확한 데이터 계약은 익명 원본 샘플과 솔루션 API 명세를 확보한 뒤
  확정해야 합니다.
