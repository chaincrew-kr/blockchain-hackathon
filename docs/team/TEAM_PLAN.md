# 4인 팀 역할 및 일정

## 운영 원칙

- 전담 프론트엔드 담당자는 두지 않습니다.
- 네 명 모두 `핵심 책임 영역 1개 + 연결되는 프론트 화면 1개`를 맡습니다.
- 책임자는 혼자 개발하는 사람이 아니라 해당 영역의 결정·통합·완료를 책임집니다.
- 7월 26일 기획이 끝난 뒤에는 핵심 범위를 추가하지 않습니다.

## 역할 분담

| 팀원 | 핵심 책임             | 함께 맡을 프론트 영역                 | 추가 책임                  |
| ---- | --------------------- | ------------------------------------- | -------------------------- |
| A    | Product / Integration | 앱 구조, 라우팅, 공통 레이아웃        | 일정, API 계약, 통합 PR    |
| B    | AI Agent / Payment    | 에이전트 실행·결제 상태 화면          | x402/pay.sh, 예산 정책     |
| C    | Backend / Cloud       | API 결과·서버/배포 상태 화면          | API, Docker, 배포, 로그    |
| D    | UX / Demo             | 결과 화면, 디자인 시스템, 반응형 마감 | 제품 문서, 발표, 데모 영상 |

각자 자기 화면의 API 연결과 오류 상태까지 직접 완성합니다. 공통 UI 규칙은 D가 기준을
잡되 구현은 네 명이 나눕니다.

## 기획 기간 — 7/23~7/26

### 7/23: 문제와 목표 확정

- 전원: 해결할 문제, 사용자, 한 줄 소개 합의
- A: 의사결정 기록과 일정 관리
- B: 에이전트가 언제 결제하는지 사용자 흐름 작성
- C: 구현 가능성, 배포 환경, 외부 의존성 확인
- D: 경쟁 서비스, 제출 형식, 데모 메시지 정리

산출물: 한 줄 설명, 핵심 사용자, 성공 기준 3개

### 7/24: 제품 흐름과 기술 구조

- 전원: `요청 → 402 → 결제 → 결과` 전체 흐름 합의
- A: 화면/API/에이전트 사이 인터페이스 정리
- B: x402 직접 연동과 pay.sh 사용 범위 확정
- C: API와 Docker/클라우드 구조 확정
- D: [Refero](https://refero.design/)에서 화면별 참고 사례를 고르고 와이어프레임 작성

산출물: 아키텍처, API 계약, 와이어프레임

### 7/25: 데모 역산과 작업 분해

- 전원: 3분 데모를 실제로 한 번 진행
- A: 기능을 작은 이슈와 PR 단위로 분해
- B: 결제 성공/거절/잔액 부족 시나리오 정의
- C: Devnet, 지갑, 배포 환경 준비
- D: 화면별 문구와 로딩·오류·성공 상태 설계

산출물: 개발 백로그, 데모 시나리오, 테스트 케이스

### 7/26: 기획 동결과 개발 준비

- 전원: Must / Should / Won't 범위 최종 결정
- 각자 담당 화면의 빈 페이지와 인터페이스 준비
- `dev` 통합, 실행 방법, 환경변수, PR 규칙 점검
- 막히면 제거할 기능의 우선순위까지 합의

산출물: 동결된 MVP 범위, 담당자, 개발 가능한 저장소

## 전원 개발 기간 — 7/27~8/2

### 7/27: 세로 한 줄 완성

네 명이 함께 최소 흐름 하나를 끝까지 연결합니다.

```text
프론트 버튼 → API 요청 → 402 확인 → 화면 표시
```

디자인보다 실제 연결을 우선합니다.

### 7/28: 결제 연결

- B 중심: 에이전트 결제 및 재요청 구현
- C: API/x402와 Devnet 환경 연결
- A·D: 결제 대기/승인/실패 UI 구현
- 종료 전 전원 E2E 확인

### 7/29: 핵심 제품 기능

- 에이전트가 실제 유료 작업 하나를 수행하도록 연결
- 각자 담당 화면의 정상·로딩·오류 상태 완성
- mock 데이터를 제거하고 실제 API 응답 사용

### 7/30: 통합 및 프론트 공동 작업

- 오전: 기능별 PR을 `dev`에 통합
- 오후: 네 명이 함께 프론트 동선과 상태 표현 정리
- 모바일/노트북 데모 해상도 확인
- API/프론트 타입과 문구 통일

### 7/31: 기능 동결

- 새로운 기능 추가 중단
- 배포, 로그, 오류 처리, 새로고침 복구 점검
- Devnet 결제 3회 이상 반복 테스트
- 심각한 버그만 수정

### 8/1: 제출물 제작

- 전원: 전체 데모 리허설과 실패 복구 확인
- D 중심: 영상 촬영·편집과 제품 문서 취합
- A: 발표 흐름과 제출 체크리스트
- B: 결제 설명과 Explorer 증거
- C: 배포 URL과 재현 방법 확인

### 8/2: 최종 검수 및 내부 완성

- 오전: 다른 PC와 시크릿 창에서 최종 테스트
- 오후: 영상, 문서, 저장소, 배포 URL의 제출 후보본 확정
- 이후 공식 제출 전까지는 치명적 버그만 수정

## 매일 개발 루틴

1. 시작 15분: 오늘 완료할 결과를 한 문장씩 공유
2. 오전: 각자 핵심 책임 영역 개발
3. 오후: 담당 프론트 화면 연결
4. 종료 30분: `dev`에서 E2E 실행
5. 막힌 일은 다음 날로 넘기기 전에 축소·우회·제거 중 하나를 결정

## PR 리뷰 조합

- A ↔ C: API 계약, 통합, 배포 변경 상호 리뷰
- B ↔ D: 결제 흐름, 사용자 상태, 데모 변경 상호 리뷰
- 지갑/개인키/정산 변경은 B와 C 중 한 명의 추가 확인 필수
- 공통 UI 변경은 D가 일관성만 확인하고 구현을 독점하지 않음
